## ADR-08：首个 Provider 采用 OpenAI 兼容端点 + Fake Provider 双轨

- **状态**：接受
- **背景**：OQ-01 要求决定"首个 VLM 参考实现采用自托管还是用户自有 API"。ADR-07 已排除维护者付费的公共端点，因此"项目托管一个网关给所有人用"不在选项内。
- **决策**：
  1. 参考实现 = **任意 OpenAI 兼容的 HTTP 端点**（`POST /v1/chat/completions`，多模态 messages）。用户填 endpoint + key + model 名即可用。
  2. 同时提供 **FakeVlmProvider**，回放固定样本，作为 G0/G1 与 CI 的默认 Provider。
  3. 自托管 vLLM（或等价）**只作为文档化路径**，不进入 MVP 交付物；不为它维护部署脚本。
- **理由**：
  - 无 GPU、无账号即可开发与测试（当前工作机已验证无 CUDA、无 Docker），Fake 轨让 90% 逻辑可在本机跑通。
  - 兼容端点覆盖面最广，用户可接自建、可接商业 API，符合 ADR-07 的"用户自配"。
  - 不绑定厂商意味着许可证审查落在"用户实际使用的模型"上，项目自身不承担分发权重义务。
- **后果**：
  - 契约测试必须同时跑 Fake 与"一个兼容端点"两条路径，否则会写出只在 Fake 下成立的代码。
  - `ProviderCapabilities` 需声明 `api_shape=openai_chat`，便于将来接入非兼容形状（如专用 SDK）。
  - 结构化输出依赖 `response_format=json_schema`；端点不支持时由网关做一次转换，失败返回 `PROVIDER_BAD_RESPONSE`（TDD §7 已有此规则）。
- **复核触发**：若 M1 发现兼容端点普遍不支持可靠 JSON Schema，才重新评估是否引入专用适配。

## ADR-09：自动观察首次开启采用分级引导

- **状态**：接受
- **背景**：OQ-05 在"一次性说明"与"每次开启确认"之间未决。
- **决策**（三级）：
  1. **首次开启**：完整三项风险说明（非导航定位；会持续消耗云端配额；描述可能出错），用户明确确认后方可开启。
  2. **此后每次开启**：仅播报一句状态（"自动观察已开启，云端用量上限每日 300 次"），**不重复长说明、不要求二次确认**。
  3. **曾因预算被中断过**：再次开启时追加一句"上次因用量上限暂停"，仅一次。
- **理由**：每次确认会显著增加操作负担——目标用户本来就最怕繁琐交互；而风险信息在首次已充分告知，重复说明不产生新保护，只产生摩擦。用"状态播报 + 配额可见"替代重复确认，既保持知情又降低负担。
- **后果**：TEST-CFG-002 的通过标准据此细化；若共创测试显示用户仍误以为自动模式=避障，升级为每次确认（保留 OQ-05 的复核入口）。
- **复核触发**：M3 共创测试若出现"用户以为自动模式在做避障"的观察，立即升级。

## ADR-10：预算默认值

- **状态**：接受（数值可调，M4 用实测成本基线复核）
- **背景**：OQ-06 要决定 NFR-COST-002 的阈值与是否允许上调。
- **决策**：

| 维度 | 默认值 | 可调范围 | 达 80% | 达 100% |
|---|---|---|---|---|
| 每日云端请求数 | 300 次 | 100–3000 | 播报一次提醒 | 暂停自动模式 |
| 每日估算费用 | ¥3.00 | ¥1–¥30 | 同上 | 同上 |
| 单会话请求数 | 100 次 | 50–1000 | 不提示 | 暂停自动模式，手动可继续 |

- 用户可上调，**硬顶为默认值的 10 倍**，且上调时必须读出一句"预计日费用将升至约 ¥X"。
- 未知 token 时费用按保守上界估算，宁可提前触发（TDD §13 已要求不得按 0 计）。
- **不允许关闭预算保护**，只能调整阈值。
- **理由**：300 次/日 ≈ 以 20s 冷却计算的自动模式约 1.7 小时满负荷，覆盖典型通勤使用；¥3.00 与单次约 ¥0.01 的估算自洽。设上限而不设开关，是因为该保护一旦可关，最可能关掉它的正是最需要它的人。
- **后果**：TDD §13.1 的"阈值待定"改为上述具体值；TEST-COST-001/002 的用例值据此固定。
- **复核触发**：M4 真机成本基线出来后按实测单价重算 ¥ 值，次数口径保留。

## ADR-11：音频焦点策略

- **状态**：接受
- **背景**：OQ-07 要决定是否在部分机型请求短暂焦点。v1.1 SDD §12 只写了"默认不请求独占焦点"，未给可实现的字面值。
- **决策**：
  1. 播报前请求 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`，播报结束立即 `abandonAudioFocus`；**最长驻留 10s**，超时强制放弃（防止 TTS 卡死导致永久压低其他音频）。
  2. **不请求 `GAIN_TRANSIENT` 或独占焦点**——那会让交通声等环境音被静音，与 PRD §3.2「不以音量遮盖环境声音」直接冲突。这是安全约束，不是体验偏好。
  3. TalkBack 开启时（`AccessibilityManager.isTouchExplorationEnabled`）**不请求焦点**，且仅在用户显式操作后延迟 400ms 播报，避免抢话。
  4. 持续时间 >25 字的文本在 TalkBack 开启时只播前 25 字 + "详情在屏幕上"，减少碰撞窗口。
- **理由**：DUCK 是把其他音频压低而非静音，在不牺牲环境音安全性的前提下保证可听清；这正好落在"可听清"与"不遮蔽"的窄区间上。
- **后果**：FR-ACC-003 的默认策略由"不请求独占焦点"细化为上述四条；TEST-ACC-003/004 依此断言。实现需处理 `AUDIOFOCUS_LOSS_TRANSIENT` 的恢复。
- **复核触发**：若真机上 DUCK 导致自播报被音乐/导航完全盖住，改为对"非 TalkBack 且非导航在播"的窄条件请求 `GAIN_TRANSIENT`。

## ADR-12：自动模式冷却开发默认 20s

- **状态**：接受（开发默认，共创后调）
- **决策**：`cooldown_ms` 默认 20000；可配 10000–60000。冷却从上一次相关播报**结束**起算（SDD §9 已定）。
- **理由**：20s 对应自动模式上限约 180 次/小时，与 ADR-10 的 300 次/日额度匹配，不会出现"额度半小时就烧完"的错配。留作 OQ-02 的调参入口。
- **后果**：TEST-TRG-001（静止 10 分钟不重复）与 TEST-TTS-004（冷却去重）使用该默认值。

## ADR-13：最低系统版本与参考设备

- **状态**：接受
- **决策**：
  1. `minSdk = 26`（Android 8.0）。
  2. 参考设备两类，缺一不可：
     - **低端**：Android 8–10，≈2 GB RAM，中低端 SoC；
     - **主流**：Android 12+，≥4 GB RAM。
  3. 性能与功耗数字必须标注具体机型 + 系统版本，否则不得引用（与 05 §4.1 一致）。
- **理由**：26 是 CameraX + Compose + 现代 TalkBack 行为都能稳定工作的下界；再往下会让无障碍与后台策略出现分支成本，而视障用户设备往往偏旧、偏中低端，低端参考机比旗舰机更能代表真实体验。
- **后果**：CI 至少编译 `minSdk 26` 变体；真机测试清单固定为上述两类。

## ADR-14：评测数据集体量

- **状态**：接受
- **决策**：
  1. **基线集**：≥300 张静态图，覆盖 8 类（室内、室外静止、光照变化、遮挡、模糊、透明物体、小目标、文字/空场景），每类 ≥30。
  2. **对抗集**：≥150 条，必含中英混合、空格拆字、否定句（"不是不能走"）、括号藏建议、OCR 文本注入。
  3. 对抗集的通过标准是**播报放行数 = 0**（PRD §11、TEST §3.2 已定），不是"准确率 ≥X%"。
- **理由**：150 条对抗样本在 0 放行的准则下，足以让单条绕过策略的漏网在标注阶段就暴露；300 张基线图是能在单人标注预算内、又足以看出场景分档差异的最低量级。
- **后果**：`evaluation/` 目录按此规模建；数据来源授权记录进 `DATA_CARD.md`。

## ADR-15：`research/01~03` 作废为需求依据

- **状态**：接受（不可逆：作废后不能假装曾有依据）
- **背景**：00 §8 引用的三份调研在工作区不存在。
- **决策**：
  1. 三份材料**正式作废为"需求依据"**，降级为"若日后找到则可作参考"的可选材料。
  2. v1.1 文档集**自足**：任何需求不得引用其结论。成本模型已由 PRD §9 参数化公式承担；专利与许可判断已由 00 §5.5 + `THIRD_PARTY_NOTICES.md` 文件级核对流程承担。
  3. **对外与本套文档中，一律不主张"已完成专利检索"或"已核实无专利风险"。** 只主张"已建立文件级许可证核对流程"与"已主动规避导航决策类功能"。
- **理由**：一份不存在的调研既不能支撑需求，也不能支撑合规声明；继续引用它制造的是虚假的可追溯性，比没有更危险。真正能承担的替代物是参数化成本公式与文件级核对流程，这两个都已经在文档里。
- **后果**：REVIEW_v1.md 中该条从"缺失待补"改为"已决作废"；若日后补回，按"可选参考"归档，不回溯改需求。

## ADR-16：共创合作方与项目命名的时点约束

- **状态**：接受
- **决策**：
  1. **共创**：M0 不承诺任何合作方，也**不开展真人共创**；M1 结束前完成"知情同意书 + 陪同机制 + 退出流程"三件套模板，合作方在 M2 前确定。在此之前所有测试限于研发内部与受控静态环境（G0/G1）。
  2. **命名**：`Kanjian` 仅为工作代号。**公开发布前必须完成商标检索**；若检索冲突，须在 M5 前改名。文档与代码中**不得出现"已完成商标检索"的表述**（当前 00 §开头已正确标注"须检索"）。
  3. 为降低改名成本：包名与展示名集中在单个资源/常量处，不散落在代码中。
- **理由**：合作方与商标都是外部事实，M0 无法也不应"决定"其结果；能决策的是**时点与禁止项**——什么时候必须完成、在此之前不得对外声称什么。把"无法决策的事"转成"有截止时间的约束"，才是可执行的决策。
- **后果**：M5 发布检查表新增"商标检索完成"一项；未完成即阻断公开发布。
